# 取引一覧・月別集計 設計書

日付: 2026-08-10

## 目的

登録済みの収支データを、月ごとに一覧表示・集計できるようにする。あわせて、登録ミスの修正や取り消しができるよう、編集・削除機能も設ける。

前回の[収支登録フォーム 設計書](2026-08-09-income-expense-entry-design.md)で作った`transactions`テーブル・登録処理（`createTransaction`）を土台とする。認証・自動テストは引き続きスコープ外。

## 画面構成

新しいページ`app/transactions/page.tsx`（一覧・集計ページ）を追加する。トップページ（登録フォーム）から、このページへのリンクを設置する。

表示順（上から下）：
1. 月切り替え（「◀ 前月」「2026年8月」「翌月 ▶」）
2. 月別集計（合計収入・合計支出・差額、カテゴリ別内訳）
3. 取引一覧（その月の取引を日付の新しい順に並べたリスト）

表示する月は、URLのクエリパラメータ`month`（例: `/transactions?month=2026-08`）で管理する。未指定の場合は今日の月を表示する。「前月」「翌月」ボタンは、`month`の値を1ヶ月分ずらしたリンク（`<a>`タグ）にする——クリックしてもJavaScriptの状態管理は不要で、URLが変わるだけでページが再取得される。

### 取引一覧の各行

日付・種別（支出/収入）・カテゴリ・金額・メモ・「編集」リンク・「削除」ボタン

### 月別集計の内容

- 合計収入・合計支出・差額（収入 − 支出）
- カテゴリ別の内訳（支出・収入それぞれ、カテゴリごとの合計金額）

集計はDBに専用のSQLクエリを投げるのではなく、一覧表示用に取得したその月のデータをJavaScript側でその場で合計する方式にする。件数が少ないうちはシンプルで十分なため。

## データ取得方式

`app/transactions/page.tsx`はServer Component（サーバー側でデータを取得してから画面のHTMLを組み立てる部品）とする。登録フォームがServer Actionでサーバー側にデータを保存しているのと同じ考え方で、一覧取得もサーバー側で行う。

- ページを開いたタイミングで、サーバー側から`lib/supabase/server.ts`の`createServerSupabaseClient()`を使い、`transactions`テーブルから対象月（`date`が該当月の範囲内）のデータを取得する。
- クライアント側でのfetch呼び出しは不要。

## 編集・削除

### 削除

一覧の各行に「削除」ボタンを置く。ボタンはクリック時にブラウザ標準の確認ダイアログ（`confirm()`）を表示し、OKならServer Action `deleteTransaction(id)` を呼び出して該当行を削除する。削除後は同じ一覧ページ（同じ月）に留まる。

### 編集

一覧の各行に「編集」リンクを置き、`app/transactions/[id]/edit/page.tsx`（編集ページ）に遷移する。編集ページは、対象の取引データをSupabaseから取得し、登録フォームと同じ構成（収入/支出切り替え・日付・金額・カテゴリ・メモ）に初期値として反映したフォームを表示する。保存すると Server Action `updateTransaction(id, formData)` を呼び出してDBを更新し、一覧ページ（元の月）に戻る。

- 存在しないIDで編集ページにアクセスした場合は、「取引が見つかりません」というメッセージを表示する。

### 新設するServer Action

`app/actions/update-transaction.ts`・`app/actions/delete-transaction.ts` を新設する。登録用の`create-transaction.ts`と同じ制約（ファイル先頭に`"use server"`、async関数のみexport）に従う。入力チェック（金額・日付・カテゴリの必須チェック）は`createTransaction`と同じ内容を踏襲する。

## エラー処理

- 一覧取得時にSupabaseとの通信でエラーが発生した場合：エラーメッセージを表示する（データなしの空一覧としては扱わない）。
- 削除・更新時の通信エラー：登録フォームと同じパターンで、エラーメッセージを表示し、ページに留まる（例外を投げっぱなしにしない）。

## セキュリティ

RLS（Row Level Security）は引き続き全許可のまま変更しない（認証未導入のため）。この設計でも新たなセキュリティ考慮は発生しない。

## テスト方針

自動テストは今回も導入しない。`npm run dev`でローカル起動し、以下を手動で確認する。
- 複数月にまたがるデータを登録した状態で、月の切り替えが正しく機能すること
- 集計金額（合計・カテゴリ別内訳）が実際のデータと一致すること
- 編集・削除が実際にSupabase側のデータに反映されること
- 存在しないIDで編集ページを開いたときにエラー表示になること

## スコープ外（今後の課題）

- グラフ表示
- 認証（NextAuth.js）とそれに伴うRLSの見直し
- 自動テストの導入
- 現金以外の支払いの自動登録（カード利用通知メールの自動読み取り、フェーズ2）
